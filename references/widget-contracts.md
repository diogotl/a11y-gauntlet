# Widget contracts

The expected behaviour of each common widget: role, states, keys and focus. Compare every custom or customised widget in the project against its contract. Each row has an ID for the report. Default severity is **Serious** unless marked.

How to apply:

- Check the rendered result, not only the source: names, roles and states in the accessibility tree, and behaviour on Tab, arrows, Enter, Space, Escape, Home/End and type-ahead.
- If the widget comes from a library, check the app did not break the contract: replaced the rendered element with a generic one, removed a required part (title, label, panel), overrode `role`, `tabIndex` or `aria-*`, or swallowed key events.
- Every contract also implies FOCUS-01 (visible focus) and NAME-02 (accessible name).
- **Variants are not failures.** Where a row says "variant", more than one implementation is legitimate. Report a variant only when it leaves a real user blocked, and say which variant you found.
- Where the contract depends on a feature the app does not have (no submenus, no chips, no touch), skip it.

Tiers:

- **Core**: what a user feels. Names, roles, states, keys, focus, Escape, focus return. Check on every widget, library-made or hand-built.
- **Deep**: implementation depth (timings, hover intent geometry, scroll-lock mechanics, IME edge cases, touch arbitration, platform quirks, positioning). These rows live in `widget-contracts-deep.md`, not in this file. Load that file only for **hand-built widgets** (plain DOM scripting, a `div` with role and handlers written in the project) or when the user passes `--deep`. A widget imported from a primitives library gets these from the library, so for it check the Core rows here and verify the app did not break the contract. Core rows may cite Deep IDs (for example `LAYER-38`) for the detail behind a statement.

Legend: **trigger** = the control that opens a layer. **popup** = the layer. **item** = option / menu item / tab.

## Cross-cutting layer contract (dialogs, popovers, menus, selects, drawers, tooltips, previews)

| ID | Tier | Contract |
| --- | --- | --- |
| LAYER-01 | Core | The trigger exposes `aria-expanded` (`true` when open, `false` when closed) and, while open, `aria-controls` pointing at the popup id. `aria-controls` must be absent (or point at an existing element) when the popup is closed or unmounted; never at a missing id |
| LAYER-02 | Core | The trigger exposes `aria-haspopup` with the popup's role (`dialog`, `menu`, `listbox`, `grid`) when the popup is not a simple disclosure. Filterable menu: when the popup holds a search input, the trigger exposes `dialog` (the popup is the dialog and the inner list is the menu); a submenu trigger exposes `dialog` only when that submenu is itself filterable, and a plain submenu inside a filterable menu keeps `menu` |
| LAYER-03 | Core | The popup has the correct role (see each widget) and an accessible name (`aria-labelledby` to its title, or `aria-label`). The name and description follow the title and description parts when they change, mount or unmount. When a naming element is replaced by another (old and new coexist for a moment, then the old one unmounts), the reference points at the newer element and the old one's cleanup never clears it |
| LAYER-04 | Core | Escape closes only the innermost layer, one layer per press, also when focus is on `<body>` or the layers share no tree. A completed press outside the whole stack closes every layer in the stack together (default); a press inside the parent but outside the child closes only the child and leaves the parent open. Variants (Review, not failures): a stack where each outside press closes only the innermost layer, or where an inner layer lets Escape continue to the layers below. A non-modal layer inside another (a select inside a popover) closes alone on Escape and, when opened programmatically from a button in the parent, returns focus to that button with the parent still open |
| LAYER-05 | Core | While an IME composition is in progress (`event.isComposing`, `keyCode 229`), Escape does not close, Enter does not select, arrows that pick a candidate do not move the highlight, and navigation or submenu keys are not acted on |
| LAYER-06 | Core | Outside dismissal fires on a completed press (click: press and release outside), not on pointer down. A right-button press, a mouse drag past a threshold, or a multi-touch gesture (a second active finger, two fingers lifted together, two fingers moving) does not dismiss. Touch variant (acceptable): for a non-modal or focus-trap-only layer, a single finger that moves past about 10 px outside dismisses at once (scroll-away) and a tap with small movement dismisses on touch end. Modal layers close on Escape and a visible close control; outside press only when it is safe |
| LAYER-07 | Core | On open, focus moves to the right place (first control, the item, the popup container, or an explicit target). On close, focus returns to the trigger, or a sensible alternative when the trigger no longer exists. Keyboard-opened layers always restore focus. When the popup's first control is a text input: a mouse press focuses the input; a touch or pen press focuses the popup container instead (the virtual keyboard stays closed) and a later tap on an item does not focus the input; a screen-reader (virtual) press focuses it synchronously. A layer opened by hover does not take focus at component level, whatever the pointer; keyboard activation of a hover-opened trigger or submenu does enter it. If a hover-opened layer is confirmed by a click before the hover delay finishes, it behaves as click-opened: focus moves in and returns to the trigger on close. A hover-opened layer closed with Escape or its own close control returns focus to the trigger even though it never had focus; one closed because the pointer left does not move focus, and an already focused trigger stays focused |
| LAYER-08 | Core | Closed popups are removed from the accessibility tree (`hidden`, `inert`, unmounted or `display:none`) while kept or animated. A closed popup that stays mounted leaves no tab stop: when focus leaves it by Tab or it is closed imperatively, any item that held the roving tab stop goes back to `tabindex="-1"`, so Tab never lands in a hidden list later |
| LAYER-12 | Core | Arrow, Home and End key events handled inside a popup do not bubble to a parent composite (toolbar, list, menu) and move its focus. This includes keys pressed on controls portalled out of the popup but owned by it: the list highlight does not move. Ordinary keys still bubble |
| LAYER-14 | Core | A disabled trigger does not open its layer by hover, focus, click, touch or keyboard; if it becomes disabled while open, the layer closes. A non-native disabled trigger or close control exposes `aria-disabled="true"`, is out of the Tab order and ignores clicks; a native disabled one leaves the focus order. **Tooltip exception:** a tooltip on a control that is only soft-disabled (`aria-disabled`, still focusable, for example a toolbar button kept discoverable) may still open on hover so the reason can be learned; only a natively disabled trigger or a disabled tooltip root suppresses opening. When one popup is shared by several triggers and the active one is open, hovering or focusing a different trigger that is disabled closes it. If the owner keeps a disabled layer open (controlled), its content is inert: no activation, no type-ahead, no submenu opening |
| LAYER-15 | Core | Tab from an open non-modal layer (from its content or its trigger) closes it and moves focus to the next focusable element after the trigger in DOM order, computed from the tab order at that moment (a neighbour that was disabled, hidden, given `tabindex="-1"`, removed, inserted or reordered while the layer was closing is respected); focus stays on that destination after the exit transition. Shift+Tab moves to the trigger or before it. Focus never lands on a hidden element; when no outside control is tabbable focus returns to the trigger, and the trigger's own tabindex is left unchanged. A menu is not a focus trap even when modal: Tab leaves, closes it and moves on. Hover-opened, touch-opened and assistive-technology-click-opened menus never hide the rest of the page. In nested menus, Shift+Tab from a submenu item closes only that submenu and focuses its trigger; Tab or Shift+Tab inside a dialog opened from a menu item closes neither the dialog nor the menu. Inside a modal dialog the dialog's own trap still wins |

## Dialog, alert dialog and drawer

| ID | Tier | Contract |
| --- | --- | --- |
| DLG-01 | Core | Popup has `role="dialog"` (or `role="alertdialog"` for urgent confirmation). Native `<dialog>` opened with `showModal()` satisfies this |
| DLG-02 | Core | Name from a visible title (`aria-labelledby`) and, when helpful, a description (`aria-describedby`). A modal without a name is a failure |
| DLG-03 | Core | Modal: focus moves in on open and is contained while open (Tab and Shift+Tab wrap), and the rest of the page is unreachable by keyboard and screen reader (`inert`, preferred). **Blocker** when the page behind stays focusable or readable. **Variants that pass:** `inert` on the rest of the page; or `aria-hidden` on every outside sibling plus a Tab trap, because the page behind is unreachable by keyboard and by screen reader cursor. **Variant that does not:** a focus-trap-only modal with the page behind still readable. That is Moderate, or Serious if a screen reader cursor can operate the page behind |
| DLG-04 | Core | Escape closes a regular dialog. An alert dialog may require an explicit choice, and then outside press stays disabled (also after remount while open), but it must still be keyboard operable |
| DLG-05 | Core | Focus returns to the trigger on close |
| DLG-06 | Core | Alert dialog initial focus goes to the safest action (Cancel), not the destructive one |
| DLG-07 | Core | Visible, named close control for non-alert dialogs; backdrop is not the only way out. The backdrop is `role="presentation"` |
| DLG-09 | Core | The dialog does not open on page load unless it is the single purpose of the screen |

| POP-02 | Core | Popup with interactive content has `role="dialog"` and is named and described (`aria-labelledby` title, `aria-describedby` description). Non-modal: no focus trap and the page remains reachable |

## Menu, context menu and menubar

| ID | Tier | Contract |
| --- | --- | --- |
| MENU-01 | Core | Trigger: button with `aria-haspopup="menu"`, `aria-expanded`. Popup `role="menu"` with `menuitem`, `menuitemcheckbox`, `menuitemradio`, `group` (named) and `separator` children. **Filterable menu** (the popup holds a filter input): the trigger has `aria-haspopup="dialog"`, the popup is a named `role="dialog"`, and the inner list is the `role="menu"` element, also labelled by the trigger, carrying `aria-orientation` when horizontal (none on the dialog). A submenu trigger gets `dialog` only when that submenu is itself filterable. An explicit `aria-label` or `aria-labelledby` on the popup replaces the trigger-based name |
| MENU-02 | Core | Only for actions. Site navigation and link lists are not `role="menu"` (use a disclosure with links) |
| MENU-03 | Core | Open with Enter, Space and ArrowDown (focus first item); ArrowUp focuses the last item. A list opened by an assistive-technology press (virtual click or virtual pointer event) focuses the first item as for keyboard when focus lives in the list; when focus stays on an input it does not; a real pointer open highlights nothing unless an item is selected, in which case that item is highlighted and scrolled into view. Context menus open with the context-menu key and Shift+F10, and on touch with a long press: movement of a few px keeps the press pending, movement beyond about 10 px, touch end, or a second touch joining (even if it then lifts) cancels it and nothing opens. With nested context-menu surfaces, opening on the inner surface opens only the inner menu. They do not block the native menu when disabled |
| MENU-04 | Core | Inside: ArrowUp/Down move (roving focus, one tab stop), Home/End jump, typing a character jumps to the next item starting with it, Enter and Space activate. Arrow keys skip group labels and separators |
| MENU-05 | Core | Escape closes and returns focus to the trigger; Tab closes and follows LAYER-15. A context menu puts DOM focus on the popup itself (not an item) when it opens, and Escape, Tab or Shift+Tab return focus to the surface that had focus before |
| MENU-06 | Core | Checkbox and radio items expose `aria-checked`; radio items live in a named group |
| MENU-07 | Core | Disabled items are reachable by arrows, expose `aria-disabled="true"` and do nothing when activated. A natively `disabled` button item is skipped instead. Disabling a whole radio group keeps its items focusable by arrows with no activation or value change, as for individually disabled radio items; an item reached by drag-release is focused, not activated |
| MENU-08 | Core | Submenus: trigger item has `aria-haspopup="menu"`; ArrowRight (ArrowLeft in RTL) opens, ArrowLeft closes and returns focus to the parent item. `aria-expanded` should reflect the state; some screen-reader workarounds omit it when opened by keyboard, so treat that variant as **Review**, not a failure, when `aria-haspopup` is present and the submenu works |
| MENU-09 | Core | Group label is hidden from the accessibility tree and the group is named by `aria-labelledby` pointing at it; when group labels swap (the old one unmounts after the new one mounts) the reference follows the newest label and the older cleanup never clears it |
| MENU-10 | Core | Item activation closes the menu (unless a checkbox/radio item opts to stay open) and returns focus |
| MENU-11 | Core | A horizontal menu sets `aria-orientation="horizontal"`; vertical omits it (the default). In a horizontal filterable menu with nothing highlighted, ArrowLeft/ArrowRight keep moving the caret and ArrowDown/ArrowUp enter the results from the start or end; once an item is highlighted ArrowLeft/ArrowRight move between items, and opening from the trigger with ArrowDown highlights the first item |
| MENU-12 | Core | Popup name defaults to the trigger label; an explicit `aria-label` or `aria-labelledby` overrides it |
| MENU-13 | Core | Filterable menu: the filter input is a search text box (`role="searchbox"` or `type="search"`, with search input mode and autocomplete, spellcheck and autocorrect off), is not exposed as a combobox and has no `aria-expanded`; it has a name, keeps real focus, has `aria-controls` pointing at the list (following id changes) and `aria-activedescendant` only once an item is highlighted. The input is a stop in the arrow loop: ArrowUp from the first item moves to the input and clears `aria-activedescendant`, a further ArrowUp wraps to the last item, and ArrowDown from the last item returns to the input. Home/End are caret keys whenever the query is non-empty, even after an item is highlighted; they move the highlight to the first or last item only when the input is empty and an item is highlighted. With text in the input, ArrowLeft/ArrowRight on a highlighted plain item only move the caret, and on a highlighted submenu trigger they open or close it only with the caret at the end or start. Enter does nothing when nothing is highlighted. The result count or empty state is announced; a filtered-out group hides its label too. The filter field is announced by its name as an edit or search field It exposes `aria-autocomplete="list"` because the list is filtered by what is typed. |
| MENU-15 | Core | Menubar: `role="menubar"` with `aria-orientation` when vertical; one tab stop; main-axis arrows move between top-level items; Home/End jump to first/last; focusing an item does not open its menu; the open key opens it (ArrowDown for a horizontal menubar; for a vertical menubar the cross-axis arrow, ArrowRight and ArrowLeft in RTL, while the opposite arrow does nothing and ArrowDown/ArrowUp move between items without opening); top-level items of a vertical menubar are `menuitem`; moving to another top-level item while open opens that one; Right opens a submenu and Left closes it returning focus; the bar stays reachable when the first item is disabled; a disabled menubar disables its items and child menus; one outside press closes the whole tree |
| MENU-16 | Core | When a filterable menu is opened from the trigger by keyboard (Enter, Space or ArrowDown), then focus moves to the filter input and the first enabled item is highlighted via `aria-activedescendant` (ArrowUp highlights the last). A mouse open focuses the input with nothing highlighted; a touch, pen or hover open highlights nothing. Typing clears an initial highlight. Reopening after Escape highlights the first item again, but a controlled reopen after a keyboard open does not |
| MENU-17 | Core | Filterable menu Escape and Space. Escape closes the popup outright and does not clear the query first (Shift+Escape also closes); the typed text is discarded when the popup closes (also when kept mounted), so the next open shows the full list, while the closing popup keeps showing the query during its exit animation. Space in the filter input activates the highlighted item only when the input is empty, types a space when the input has text, does nothing when empty with nothing highlighted, and Shift+Space types. (This differs from a selection combobox, CMB-03, and from autocomplete text retention.) |
| MENU-18 | Core | When a filter input sits inside a popup, then it never loses real focus to the list: a press on an item, a group or a label keeps focus on the input (item mousedown is default-prevented); if the list itself receives focus (a press on a group label), focus goes back to the input, except when the input was deliberately left unfocused (touch open, to keep the on-screen keyboard closed) |
| MENU-19 | Core | When a hover-opened filterable menu has focus still on the trigger, then ArrowDown moves focus into the filter input and highlights the first item, and a printable character moves focus into the input; modified keys and cross-axis arrows leave focus on the trigger |
| MENU-20 | Core | Submenus in a filterable menu. For a plain (non-filterable) submenu inside a filterable menu, ArrowRight (mirrored in RTL) from the input with the trigger highlighted opens it and hands real focus to its first item; the close key or Escape closes it, returns focus to the input and re-highlights the trigger immediately, even while the exit animation runs; an item press that closes the whole tree does not return focus to the input; pressing the open key again while open re-enters instead of reopening, and the close key pressed while the trigger holds focus still closes it. For a filterable submenu, Escape returns focus to the parent menu's filter input, while Escape in the root menu returns focus to the trigger button |
| MENU-21 | Core | When a filterable menu root is disabled, then the filter input and Clear button are natively disabled; with the layer kept open by the owner, items cannot be activated, type-ahead cannot highlight them and submenu triggers do not open |
| MENU-22 | Core | When a filterable menu or submenu opens (by Enter, by a screen-reader activation or by ArrowRight on the submenu item), then focus is on its search input with the first item exposed as the active descendant and the screen reader announces that first item once; a later announcement of the menu or submenu name must not cancel the item announcement |

## Button

| ID | Tier | Contract |
| --- | --- | --- |
| BTN-01 | Core | Native `<button type="button">`. Set `type` explicitly: inside a form the default is `submit` |
| BTN-02 | Core | A custom element acting as a button has `role="button"`, `tabindex="0"`, activates on Enter and Space (Space on key up for non-native), dispatches a real click, carries modifier-key state, and does not scroll the page on Space |
| BTN-03 | Core | Native `disabled` removes the element from focus order and interaction and fires none of the pointer or key events; a control that becomes natively disabled while focused is blurred and its focused state clears. If it must stay discoverable, use `aria-disabled="true"` with the action blocked (click, mousedown, pointerdown and keydown handlers do not run) and focus kept, while hover and pointer-move still fire so a tooltip can explain why; it keeps focus when its own activation disables it. A custom element that is disabled has `aria-disabled="true"` and a `tabindex` that matches the focus policy (default `-1`, or deliberately focusable) |
| BTN-04 | Core | A link styled as a button keeps link semantics when it navigates; Space on a link-as-button does not scroll the page. **Review:** a link rendered through a generic button wrapper that is exposed as `role="button"` while still navigating on Enter and Space is a semantics mismatch (link role expected) even though the keyboard behaviour is correct |
| BTN-05 | Core | Toggle button: `aria-pressed` (`true`/`false`), Enter and Space toggle; the name does not change with state |
| BTN-06 | Core | Loading state keeps the label, sets `aria-busy` or `aria-disabled`, blocks repeat activation and announces the result |

## Select

| ID | Tier | Contract |
| --- | --- | --- |
| SEL-01 | Core | Prefer native `<select>`. A custom select needs a labelled trigger |
| SEL-02 | Core | Trigger `role="combobox"` (or a labelled button) with `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls` (only while open); popup `role="listbox"`; options `role="option"` with `aria-selected`; groups `role="group"` whose label is hidden from the accessibility tree and which are named by `aria-labelledby` pointing at it (the link follows the label's id changes, uses the newest label when labels are replaced and is removed when the label unmounts). A separator inside a listbox popup is exposed as presentational with no orientation, not as `role="separator"` (a listbox may only own options and groups); menu and toolbar separators keep `role="separator"`. If a wrapper surrounds the listbox, the wrapper is `role="presentation"` and the listbox carries the ARIA |
| SEL-03 | Core | Open with Enter, Space, ArrowDown, ArrowUp; Up/Down move the active option (skipping group labels and separators); Home/End; type-ahead; Enter or Space selects and closes; Escape closes without changing the value; Tab closes. When opened by keyboard with a selection, the highlight starts on the selected item. When a multi-select opens with several values selected, the initial highlight and focus go to the first selected item in rendered (DOM) order, not value order, also across groups; toggling an option keeps the popup open and keeps highlight and focus on that same option (also when deselected by Enter), and arrows continue from that anchor. Like a native select, a typeahead keypress on a closed trigger may commit the next enabled match |
| SEL-04 | Core | The current value is exposed (value text on the trigger), and the placeholder is not announced as a value |
| SEL-05 | Core | Disabled options expose `aria-disabled` and are reachable by arrows but cannot be selected by Enter, click or drag-release. Multi-select exposes `aria-multiselectable="true"` on the listbox |
| SEL-07 | Core | Required exposes `aria-required` or `required`; invalid exposes `aria-invalid` and its message; read-only exposes `aria-readonly="true"` on the trigger and listbox and commits nothing, including by type-ahead. A read-only or disabled select (inside or outside a field) also commits nothing from item clicks or Enter even when forced open, and leaves field errors untouched |
| SEL-09 | Core | When a popup is laid out directly over its trigger (item-aligned positioning), then focus landing on the trigger closes the popup so the focused trigger is not obscured (2.4.11); a popup placed beside the trigger stays open when the trigger is focused |

## Combobox and autocomplete

| ID | Tier | Contract |
| --- | --- | --- |
| CMB-01 | Core | Input `role="combobox"` with a name, `aria-expanded`, `aria-autocomplete` (`list` or `both`), `aria-haspopup="listbox"`. Closed: `aria-expanded="false"`, no `aria-controls`, no `aria-activedescendant`. Open: `aria-controls` the listbox id; `aria-activedescendant` appears only once an item is highlighted. When the list is rendered inline (always visible), the input already has `aria-expanded="true"` and `aria-controls` pointing at the list before any interaction; when the results are a grid, `aria-haspopup` is `grid` and `aria-controls` points at the grid |
| CMB-02 | Core | DOM focus stays on the input; the active option is exposed by `aria-activedescendant`, which updates on each arrow key, follows filtering, and is cleared when the list closes (reopening and pressing ArrowDown highlights the first item; typing resets the highlight to none). Pointer selection does not steal focus from the input: a mouse press on an option or on the listbox itself does not move focus, and an option chosen by touch keeps the input focused so the on-screen keyboard stays up. When focus leaves the input the highlight and `aria-activedescendant` clear and are restored when focus returns; refocusing the input while an ordinary (non-virtual-focus) list is open clears the item highlight |
| CMB-03 | Core | ArrowDown opens and moves; ArrowUp moves; Enter selects the active option. **Opening with no selection** highlights nothing until an arrow is pressed (ArrowDown highlights the first, ArrowUp the last) and typing clears the highlight. **Opening with a selection** (pointer, keyboard or an inline list on mount) highlights the selected option (the first selected in rendered order for multi-select), exposes it by `aria-activedescendant`, and arrow keys continue from it rather than from the top. Enter with no highlighted option is not prevented, so a surrounding form submits; with a highlighted option Enter selects it and does not submit; when read-only Enter never submits or commits. **Closing a selection combobox without committing** (Escape, outside press, Tab) discards the uncommitted typed query: a single-select reverts to the selected option's label (empty when none), a multi-select to empty, and the next open starts with an unfiltered list. With the popup closed, a first Escape in a single-select with a value clears the input and the selection, and in a multi-select clears the value; it moves to a clear button when one is present. Keeping the typed text on Escape only fits a non-selection autocomplete (**variant**: some designs also clear on a second Escape; both are acceptable if announced). Escape propagates to a parent only when there is nothing left to close or clear |
| CMB-04 | Core | Popup `role="listbox"`; options `role="option"` with `aria-selected`; groups named; the listbox named. In the pattern where the input lives inside the popup, the trigger is the combobox (`aria-haspopup="dialog"`, `aria-controls` the popup), the popup is `role="dialog"`, `aria-required`/`aria-readonly`/validation ARIA sit on the trigger (never on the inner input), and the wrapper around an outside input is `role="presentation"`. In that pattern pressing the trigger while open closes the popup with focus on the trigger (not the input); Enter commits the highlighted option, closes the popup and returns focus to the trigger, which shows the new value; Escape closes and returns focus to the trigger, and for a selection combobox discards the query while keeping the selection and reopens with an empty query and the selected option highlighted, whereas for a non-selection autocomplete it keeps the typed text (shown on the trigger, and in the input with the filter applied on reopen). Touch opens with focus on the popup container |
| CMB-05 | Core | Result count or "no results" is announced in a status region (`role="status"`, polite) that exists before it updates, and updates immediately after mount. The status region sets `aria-atomic="true"` so the full count is read, not just the changed digits. **Variant (Review, not a failure):** an empty-state part that mounts only when the result set is empty (no `role="status"` element in the DOM while results exist) appears with its text when results become empty; some screen reader pairs may drop that announcement, so keeping the live root mounted and toggling only its children stays the recommended pattern |
| CMB-06 | Core | Loading state is announced; stale results are not selectable while loading. When the result set is replaced under the highlight (server results, reorder, filter-less list), the highlight and `aria-activedescendant` are cleared so Enter cannot run an item the user never chose (with auto-highlight the first new item is highlighted again, also after an empty result). A late response that arrives after the user cleared the query, closed the popup or blurred the input highlights nothing |
| CMB-07 | Core | Multi-select chips: the container has `role="toolbar"` only when at least one chip exists; chips are reached by arrows from the input (Left focuses the last chip, mirrored in RTL; an arrow past the last chip lands on the input); Backspace on an empty input removes the last rendered chip (or the last selected value when no chips render), also after focus returned from a chip, and nothing is removed when read-only or disabled; when the input regains focus the chip highlight clears so ArrowLeft reaches the last chip again. On a focused chip, Backspace and Delete remove it and focus moves to the next chip (or the input when none); Enter, Space, ArrowDown, ArrowUp and unmodified printable keys send focus back to the input (ArrowDown/ArrowUp also open the popup); Ctrl/Meta/Alt combinations are ignored; focusing a chip closes an open popup, and pressing a chip does not dismiss it. Chip Remove buttons are named with the chip text and may be `tabindex="-1"` while remaining focusable; pressing one (or Space on it) removes the chip, lands focus on the input and keeps an open popup open; disabled and read-only chips expose `aria-disabled` and `aria-readonly`, the remove control of a read-only chip does nothing, and they cannot be deleted |
| CMB-08 | Core | Free text is allowed or rejected with a visible and announced rule (`aria-invalid` + message) |
| CMB-10 | Core | A visible Clear button is labelled ("Clear search") and does not trap focus. It may be `tabindex="-1"` and hidden from the accessibility tree (variant) only when the keyboard has another way to clear (emptying the input, Escape). Activating it (or clearing the typed value) empties the selection or text, moves focus to the input (or the popup's input), keeps an open popup open, and the button is not rendered while the value is empty; a disabled (native or non-native) or read-only control ignores the press |
| CMB-13 | Core | **Auto-highlight variant** (acceptable): after the user types, the first match is highlighted and exposed by `aria-activedescendant` (also after an IME composition ends and when results arrive asynchronously; updating when filtering replaces the item), Enter selects it, and nothing is auto-highlighted on plain open or on a pointer click; a pointer-hovered option is not replaced; the highlight clears when the highlighted chip is removed. | LIST-11 | Core | Opening a menu with Enter focuses the first item; if items are links they are real anchors, and Enter and Space on a link item both navigate (the URL changes; modifier state such as Ctrl/Cmd+Enter still reaches the click handler, also from a virtually highlighted link in a filter menu). With a client-side router link as the item, activating it still navigates, Back returns to the originating page, and the menu opens and works again. When an option contains an anchor, a click on a real `href` link does not select the option, a hash link closes the popup without selecting, and an anchor without `href` behaves as a normal option |
| LIST-13 | Core | When a menu, select or combobox list is opened by pointer with no selected item, then no item is highlighted (no `aria-activedescendant` for a virtual-focus list), focus is on the popup container (or stays on the input), and the first ArrowDown highlights the first item; when an item is selected, that item is highlighted and scrolled into view even for pointer opens. Closing clears the highlight, so reopening after Escape starts fresh without remembering the previous one; after keyboard navigation the pointer may take the highlight back and arrows continue from the hovered item |

## Developer responsibilities (what the app must still provide)

| ID | Tier | Contract |
| --- | --- | --- |
| DEV-01 | Core | A non-native element used as a button must still be able to take button semantics and keyboard handling. A link must not be turned into a button; a link that looks like a button is styled as a link |
| DEV-02 | Core | A button entering a loading state after activation keeps focus, and the changing text is the explicit accessible name (`aria-labelledby` on the text node), because some browser and screen reader pairs do not announce descendant text changes on a focused button |
| DEV-03 | Core | A trigger with a tooltip has its own `aria-label` or visible text that closely matches the tooltip; the tooltip is visual-only supplement. Important descriptions are not hidden behind a tooltip: use a popover that opens on hover and is reachable by touch and screen reader. Hover content must stay hoverable: a popup configured so the pointer cannot enter it (hoverable popup disabled, cursor-tracking on both axes which makes the popup ignore pointer events, or hover content with no safe-path logic so moving from trigger onto the popup closes it) fails 1.4.13 and must carry nothing not available otherwise; by default the pointer can travel from trigger to popup and the popup closes when the pointer leaves it |
| DEV-04 | Core | Every action in a context menu is also available through a visible control |
| DEV-05 | Core | A hover preview card's popup is not reachable by keyboard, touch or screen reader, so every piece of previewed information also exists at the link's destination |
| DEV-06 | Core | A high-priority toast announces only the title and description strings passed to the toast API; extra JSX inside is not announced. Essential information goes in those strings |
| DEV-07 | Core | A live status or empty-state element used for result counts keeps its root mounted; show or hide its children, never the element itself (`display:none`, `hidden`, `aria-hidden`, conditional rendering). An empty-state part that mounts only when empty is a variant: **Review**, not a failure (announcement may be dropped by some screen reader pairs). A polite region present at mount needs a text mutation after mount to be announced reliably |
| DEV-08 | Core | A popup trigger inside a toolbar is the toolbar button itself (composed), disabled on the toolbar button not on the trigger, so it stays in roving navigation; a tooltip trigger wraps the toolbar button |
| DEV-09 | Core | A modal dialog or drawer has a Close control inside the popup DOM so touch screen readers can leave it; floating close buttons that look outside the styled popup still live inside the popup element. A popover flagged modal that has no close control inside its popup is not modal in practice: the page behind is not made inert and Tab leaves and closes it like a non-modal layer; once a close control is rendered inside, the rest of the page is inert or `aria-hidden` and focus is contained |
| DEV-10 | Core | A bottom sheet or drawer with form fields keeps the focused field visible when the on-screen keyboard opens (FOCUS-02 neighbour): the field is scrolled into the visible area above the keyboard (centred, or on Android with the minimum movement; a field already visible on Android is not moved; a tall textarea that fits stays; one taller than the visible band aligns by its top), the scroll container gains enough bottom space to allow it, and that space is released when focus leaves, the field is removed or the layer closes. When the user taps a control while the keyboard is open and the tap moves focus, the layout does not shift under the finger between press and release, so the first tap activates the tapped control |
| DEV-11 | Core | One tab stop per accordion header is correct: do not flag it as a roving-focus failure. Up/Down and Home/End between headers are optional |
| DEV-12 | Core | A slider has a name: a visible label, or an `aria-label` per thumb; a multi-thumb slider needs an `aria-label` on every thumb even with a visible label. Provide `aria-valuetext` whenever the number alone is not meaningful (also for progress and meter) |
| DEV-13 | Core | Chips in a multi-select: add a description such as "Press Backspace or Delete to remove" on the chips and the input, an `aria-label` on the chips container, and "Remove X" on each remove button. OTP slots 2..N need an `aria-label` ("Character N of M") and the description linked to the group; when a field label is applied to every slot, slots 2..N still need their own names |
| DEV-14 | Core | With sibling labels (`for`/`id`) a checkbox, radio or switch whose root is not a native control needs the control rendered as a native button or input; with wrapping labels around a native control, the hidden input must sit outside the label. A non-native label (a `span`) cannot toggle a switch that is not a native button, so the label-click affordance is lost even though the label still names the switch; use a native label or a native button switch. Verify label click, focus and association |
| DEV-15 | Core | A menu filter input has its own label; the popup is a dialog holding a search input and the menu list |
| DEV-16 | Core | A custom wrapper around a form control forwards the ref to the real control, or focus-to-first-invalid breaks. Localised error messages are the app's job |
| DEV-17 | Core | A disabled layer on a trigger stops opening but does not necessarily set `disabled` on the element: check both when the intent is "disabled". For non-modal layers, disabling pointer dismissal also removes close-on-focus-leave; confirm Tab-away still behaves |
